# 工作室任务提交工作台——前端原型设计规格

日期：2026-08-01  
状态：已确认，待用户审阅规格文件

## 1. 项目目标

制作一个亮色、可点击、可完整演示业务闭环的三端前端原型：

- 用户端：注册、登录、提交单条或批量链接、查看任务状态。
- 工作室端：通过专属链接进入队列，无需登录；打开任务即开始处理，并可标记成功或失败。
- 管理员端：登录后查看数据、管理用户、查看全部任务和维护工作室入口。

原型只配置一个工作室，不包含 CDK、余额、扣费、跨工作室派单和任务转移。

## 2. 原型范围

### 2.1 包含

- React 单页应用中的用户端、工作室端和管理员端。
- 基于路由的三端入口与访问控制。
- 使用 `localStorage` 保存账号、任务、登录状态和工作室配置。
- 单条和批量链接提交。
- 排队中、处理中、成功、失败四种任务状态。
- 三端之间的任务数据联动。
- 桌面端优先并兼容手机宽度的响应式布局。
- 演示数据重置能力。

### 2.2 不包含

- 真实后端、数据库、短信、邮箱或第三方登录。
- 真实鉴权、加密、服务端权限校验或生产安全能力。
- CDK、余额、充值、扣费、支付和结算。
- 多工作室创建、工作室切换或跨工作室分发。
- 工作室账号登录、多人协作、领取任务或操作员归属。
- 任务备注、处理凭证、附件上传和聊天。

## 3. 视觉设计

### 3.1 风格

- 参考用户提供的高信息密度工作台布局，但整体改为亮色主题。
- 页面背景使用浅灰白，核心内容使用白色卡片。
- 主色使用青蓝色，强调提交、链接、选中状态和关键数据。
- 轻量边框、柔和阴影、中等圆角，形成现代 SaaS 管理后台风格。
- 不复制参考图中的 CDK、余额、合并 CDK 等元素。

### 3.2 状态色

- 排队中：橙色。
- 处理中：蓝色。
- 成功：绿色。
- 失败：红色。

状态不能只依赖颜色表达，必须同时显示文字标签。

### 3.3 响应式规则

- 大屏：侧边导航或顶部导航配合宽表格、统计卡片和详情抽屉。
- 中屏：统计卡片自动换行，表格保留横向滚动。
- 手机：列表改为卡片式摘要；详情使用全屏抽屉；主要操作按钮保持可见。

## 4. 信息架构与路由

### 4.1 用户端

- `/s/demo-studio/register`：工作室专属注册页。
- `/login`：用户账号密码登录页。
- `/user/workbench`：支付链接提交与“我提交的支付链接”工作台。

用户通过专属注册链接注册后自动绑定唯一工作室。登录用户只能查看自己的任务。

### 4.2 工作室端

- `/studio/studio-demo-8f3c2a`：工作室专属不可猜测入口。

工作室端无需登录。入口令牌与唯一工作室绑定；无效令牌显示“入口已失效”。原型仅用于交互演示，不将该链接视为生产环境安全方案。

### 4.3 管理员端

- `/admin/login`：管理员账号密码登录页。
- `/admin/dashboard`：数据概览。
- `/admin/tasks`：全部任务。
- `/admin/users`：用户管理。
- `/admin/studio`：工作室设置与入口链接。

## 5. 页面设计

### 5.1 用户注册页

- 展示工作室名称，明确注册后将绑定该工作室。
- 字段：账号、密码、确认密码。
- 校验：账号不能为空且不能重复；密码至少 6 位；两次密码必须一致。
- 注册成功后自动登录并进入用户工作台。
- 无效注册链接展示失效状态，不显示注册表单。

### 5.2 用户登录页

- 字段：账号、密码。
- 登录失败时在表单附近显示明确错误。
- 被停用的用户显示“账号已停用”。
- 登录成功进入 `/user/workbench`。

### 5.3 用户工作台

- 顶部：产品名称、所属工作室、当前用户和退出按钮。
- 提交卡片：统一多行输入框，不区分单条和批量模式。
- 每行输入一条支付链接；输入一行就是单条，输入多行就是批量。
- 单次提交不限制条数。
- 输入区域实时显示有效条数、空行数量、重复数量和错误数量。
- 提交后显示成功提示和创建的任务数量。
- 统计卡片：全部、排队中、处理中、成功、失败。
- “我提交的支付链接”列表：状态筛选、关键字搜索、提交时间、当前状态和处理时间。
- 点击任务查看详情，但用户端不允许修改状态。

### 5.4 工作室工作台

- 顶部：工作室名称、当前排队数量和刷新提示。
- 统计卡片：排队中、处理中、今日成功、今日失败。
- 队列表格默认按提交时间升序排列，确保先进先出。
- 支持状态筛选和链接关键字搜索。
- 点击“排队中”任务打开右侧详情抽屉，并立即更新为“处理中”。
- 打开已处于“处理中”的任务不重复修改开始时间。
- 详情显示任务编号、链接、支付二维码、提交用户、提交时间、开始处理时间和状态。
- 处理中任务提供可选的文字反馈输入框；“处理成功”和“处理失败”必须二选一并均需二次确认。
- 已填写的处理反馈在用户端、工作室端和管理员端任务详情中展示。
- 已成功或失败的任务只读，不能再次修改。

### 5.5 管理员端

#### 数据概览

- 用户总数、任务总数、排队中、处理中、成功和失败数量。
- 最近任务列表和状态分布。

#### 全部任务

- 按任务编号、链接或用户名搜索。
- 按状态筛选。
- 查看任务详情和完整时间线。
- 管理员仅查看任务，不直接代替工作室修改处理结果。

#### 用户管理

- 展示账号、状态、注册时间、任务总数和最近提交时间。
- 支持启用或停用用户。
- 停用操作需二次确认；停用用户保留历史任务。

#### 工作室设置

- 修改唯一工作室的显示名称。
- 复制用户专属注册链接。
- 复制工作室工作台链接。
- 显示工作室当前用户数和任务数。
- 不展示新增、删除或切换工作室的功能。

#### 演示数据

- 提供“重置演示数据”操作。
- 重置前必须二次确认。
- 重置后恢复内置管理员、演示用户、唯一工作室和初始任务。

## 6. 任务业务规则

### 6.1 链接提交

- 只接受以 `http://` 或 `https://` 开头的链接。
- 统一输入框按换行拆分，不限制单次创建数量。
- 自动忽略空行。
- 同一次提交中的重复链接只创建一次，并提示去重数量。
- 不做全局去重：用户可以在后续提交中再次提交相同链接。
- 每条有效链接创建一个独立任务。

### 6.2 任务状态机

```text
排队中 -> 处理中 -> 成功
                 -> 失败
```

- 创建任务时记录提交时间，状态为“排队中”。
- 工作室首次打开排队任务时记录开始处理时间，状态变为“处理中”。
- 工作室确认成功或失败时记录完成时间。
- 成功和失败是不可逆终态。

### 6.3 工作室归属

- 当前原型只有一个工作室。
- 用户注册时写入 `studioId`。
- 新任务继承提交用户的 `studioId`。
- 工作室端只读取与自身入口令牌对应的 `studioId` 任务。
- 数据结构保留 `studioId`，便于未来扩展多工作室，但本次界面不暴露扩展功能。

## 7. 原型数据模型

### 7.1 Studio

```ts
type Studio = {
  id: string
  name: string
  registrationCode: string
  accessToken: string
  enabled: boolean
  createdAt: string
}
```

### 7.2 User

```ts
type User = {
  id: string
  username: string
  password: string
  studioId: string
  enabled: boolean
  createdAt: string
}
```

### 7.3 Task

```ts
type TaskStatus = 'queued' | 'processing' | 'success' | 'failed'

type Task = {
  id: string
  url: string
  status: TaskStatus
  userId: string
  studioId: string
  submittedAt: string
  processingStartedAt?: string
  completedAt?: string
  feedback?: string
}
```

### 7.4 Admin

```ts
type Admin = {
  id: string
  username: string
  password: string
}
```

密码在原型中仅作为本地演示字段，不代表生产环境存储方式。

## 8. 前端技术架构

- React + TypeScript + Vite。
- React Router 负责路由和三端入口保护。
- 统一的本地仓储层封装 `localStorage`，页面组件不直接读写存储。
- Context 或轻量状态容器维护当前会话及数据刷新。
- 共享组件包括按钮、输入框、状态徽标、统计卡片、数据表格、详情抽屉、确认对话框和提示消息。
- 业务模块按 `auth`、`user-workbench`、`studio-workbench`、`admin` 和 `data` 分离。

## 9. 演示账号与初始数据

- 管理员账号：`admin` / `Admin123!`
- 演示用户账号：`demo` / `Demo123!`
- 唯一工作室：`演示工作室`
- 注册入口：`/s/demo-studio/register`
- 工作室入口：`/studio/studio-demo-8f3c2a`
- 初始任务覆盖排队中、处理中、成功和失败四种状态，便于直接演示筛选和统计。

## 10. 错误处理与反馈

- 表单错误在对应字段附近显示，避免只使用全局提示。
- 提交、状态更新、启停用户、复制链接和重置数据均提供即时反馈。
- 无数据列表显示明确空状态和下一步操作。
- 无效路由显示统一 404 页面，并提供返回入口。
- 未登录用户访问用户工作台时跳转 `/login`。
- 未登录管理员访问管理路由时跳转 `/admin/login`。
- 无效或停用的工作室入口显示失效页。

## 11. 可访问性与交互质量

- 所有表单控件具备可见标签。
- 键盘可以完成登录、提交、筛选、打开详情和确认操作。
- 焦点样式清晰；抽屉和对话框打开后正确管理焦点。
- 状态变化使用文字、颜色和图标共同表达。
- 按钮加载或提交期间禁用重复操作。
- 复制链接提供成功或失败提示。

## 12. 验收标准

1. 用户能从专属注册链接注册并自动绑定唯一工作室。
2. 用户能使用账号密码登录和退出。
3. 用户能提交单条链接。
4. 用户能通过统一输入框提交任意数量的链接，并看到去重及错误提示。
5. 每条有效链接生成独立的排队任务。
6. 工作室专属入口无需登录即可查看唯一工作室队列。
7. 工作室打开排队任务后，任务自动变为处理中并记录开始时间。
8. 工作室能将处理中任务标记为成功或失败，终态不可逆。
9. 用户端和管理员端能看到工作室更新后的状态。
10. 管理员能查看统计、筛选任务、启停用户和复制两个专属入口。
11. 页面刷新后，本地数据和登录状态按预期保留。
12. 重置演示数据后恢复指定演示账号、工作室和初始任务。
13. 桌面和手机宽度下主要流程均可操作，无明显遮挡或溢出。

## 13. 后续正式系统的替换边界

正式开发时，可保留页面、组件和业务状态机，将本地仓储层替换为后端 API。生产版本还需增加服务端鉴权、密码哈希、工作室入口安全策略、数据库约束、审计日志、并发状态控制和真实权限校验；这些不属于当前可点击前端原型范围。
